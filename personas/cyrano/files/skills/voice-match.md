# Voice Match — standard write-in-voice workflow

This is the default workflow for any "write X in my voice" request
that is *not* a rewrite. (For "rewrite this in my voice", see
`/skills/rewrite-in-voice.md`.)

## Step 0 — Do you have enough to work with?

Before anything else: read `/voice/profile.md`. If it doesn't exist,
or the **Sample inventory** has fewer than ~3 substantial samples
(≥300 words combined, ideally spanning the register the user is
asking you to write in), stop and run `/skills/sample-intake.md`
to gather them. Don't bluff a voice you don't have.

If the request is for a register the profile doesn't cover (profile
is built from blog posts, request is "tweet in my voice"), ask for
a few samples in that register specifically. Voice doesn't transfer
cleanly across channels — most people are looser on Twitter than in
their newsletter.

## Step 1 — Get the substance right (content pass)

Voice is the *surface*. Underneath it there has to be an argument
worth reading. Do the substance pass *first*, in a neutral voice,
because if you try to do voice and substance simultaneously the
substance loses.

For an essay/post:
- What's the one idea the reader should take away?
- What's the inciting question or observation?
- What's the structure: hook → claim → evidence → so-what? Or
  story → reflection → claim? Or counterintuitive setup → resolution?
  Match what this author tends to do (read **Signature moves** in
  the profile).
- What facts/anecdotes/examples does the user need to plug in? If
  you're writing about *them* (a bio, a "paragraph about me"),
  what concrete biographical material do you actually have? If
  you don't have enough, ask before drafting — fabricated bio
  details are worse than a delayed draft.

Output a short outline (3–6 bullets) and confirm with the user
*if the request is non-trivial* (essay, blog post). For a
paragraph/bio/email, skip the outline-confirm step and proceed
to Step 2.

## Step 2 — Draft in voice

Write the draft against the profile. Concretely:

- Reach for the **Signature moves** explicitly. If the author opens
  with a one-sentence paragraph, do that. If they use parenthetical
  asides, use them.
- Stay inside the cadence ranges (sentence length, paragraph length).
- Pull diction from their **Words they use a lot** list when natural;
  avoid every entry on **Words they never use**.
- Match contraction habits exactly. This is one of the strongest
  voice signals and one of the easiest to get wrong.
- If the author punctuates idiosyncratically (no Oxford comma,
  spaced em-dashes, lowercase i), do it their way.

## Step 3 — Humanize pass

Read `/skills/humanize.md` and run the checklist against your draft.
Strip every AI tell you find. This is non-negotiable — you cannot
ship a draft you haven't humanized. The user is going to publish
this; an AI-detector hit lands on them.

## Step 4 — Voice bench (self-check)

Run `/skills/voice-bench.md` against the draft. Score honestly. If
you score below threshold, revise; don't ship borderline work.

## Step 5 — Deliver

Hand back the draft with a one-line note flagging:

- any spots you weren't sure about ("the third paragraph leans
  more formal than the profile — flag if that's wrong")
- any factual claims you inferred rather than knew ("I said you
  worked at X for 'about five years' — fix the number")
- any voice rules you intentionally bent and why (rare; usually
  don't)

Don't pad the delivery with "I hope this captures your voice!"
preambles. Hand the draft over and stop.

## Step 6 — Capture corrections

When the user pushes back, *every correction is a rule*. Update
`/voice/profile.md` and write a memory entry tagged with the
author. Next draft starts smarter.
